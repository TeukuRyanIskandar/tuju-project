01

Deepen the JobBus into the job lifecycle module

Strong local-substitutable
  • apps/backend/src/jobbus/job-bus.service.ts: onModuleInit() 'progress' / 'completed' / 'failed'
  • apps/backend/src/analysis/analysis-result.store.ts: persist(), findByCorrelationId()
  • apps/backend/src/jobbus/job-bus.int-spec.ts

Before: raw broadcast, routing left to subscribers

sequenceDiagram
  participant U1 as Request A
  participant U2 as Request B
  participant JB as JobBus
  participant R as BullMQ
  participant S as ResultStore
  U1->>JB: enqueue(env A)
  JB->>R: add(jobId=ta-MAYBANK-1D-T05)
  U2->>JB: enqueue(env B)
  JB->>R: add(same jobId) → deduped
  Note over JB: correlationId B never recorded
  R-->>JB: completed(returnvalue: corr A)
  JB-->>S: broadcast JobResult
  S->>S: save row for A only
  R-->>JB: failed(jobId, failedReason)
  JB-->>S: JobFailure{correlationId: '', retryable: true, userMessage: stack}

After: JobBus resolves jobId → correlationIds

sequenceDiagram
  participant U1 as Request A
  participant U2 as Request B
  participant JB as JobBus (deep)
  participant R as BullMQ
  participant S as ResultStore
  U1->>JB: enqueue(env A)
  U2->>JB: enqueue(env B)
  Note over JB: registers A, B against jobId
  R-->>JB: progress / completed / failed
  JB->>JB: fan out + classify + redact
  JB-->>S: JobResult for A
  JB-->>S: JobResult for B
  JB-->>S: JobFailure{terminal | exhausted, safe msg}

Problem. ADR-0007's fan-out isn't implemented. A second request that dedupes onto an existing job never gets its result (GET /analysis/:correlationId returns 404 forever). Progress events carry no correlationId, and every failure shows up as transient_exhausted with an empty correlationId and the raw failedReason.

Solution. The JobBus owns event routing: it records each correlationId against its jobId at enqueue, resolves them when BullMQ events arrive, classifies each failure as terminal or exhausted, and redacts the user message before anything leaves the module.

  • Locality: fan-out lives in one module
  • Leverage: subscribers receive per-correlation events
  • Fixes the silent dedup-collapse bug
  • Tests hit one interface, real Redis
  • Failure classes finally match contract

Tests: the existing testcontainers int-spec extends with "two enqueues, one jobId → both correlationIds notified" and "poison job → terminal JobFailure". The Redis-backed registry is the multi-instance adapter ADR-0007 already anticipates.

Make the Enqueue seam actually own the enqueue

Strong in-process

After: small interface, deep implementation

actor + job name + payload

Problem. Every enqueue caller has to hand-build a correct JobEnvelope, and the ADR-0005 capability check at the enqueue seam doesn't exist. can() runs only in the route guard, so the upcoming price-move trigger, or any route missing @RequiresJob, enqueues without a check.

Solution. Callers hand the enqueue seam an actor (a user, or the trusted system caller) plus the job request. The module asks can(), validates the payload against the contract, mints the envelope and applies the queue policy.

  • ADR-0005 second check becomes real
  • Leverage: price-move trigger reuses it
  • Controller shrinks to HTTP translation
  • Envelope rules gain locality
  • Unit-testable with a fake queue
Implements ADR-0005's defense-in-depth rather than contradicting it. The route-level TierGuard stays.
03

One owner for Job identity (jobId) across both worlds

Strong in-process
  • apps/backend/src/jobbus/job-bus.service.ts: deriveJobId() → "ta-MAYBANK-1D-2026-09-29T05"
  • services/ai/src/tuju_ai/handler.py: handle_job() → f"{prefix}:{symbol}:{anchor}:{bucket}"
  • services/ai/src/tuju_ai/worker.py: process(job): has job.id, ignores it
  • packages/contracts/fixtures/job-result.json, job-failure.json (colon form)

Before: two derivations, two formats

TS · JobBus

ta-MAYBANK-1D-…T05

→ BullMQ job id

Py · handler

ta:MAYBANK:1D:…T05

→ JobResult.jobId

Postgres analysis_results.job_id ≠ BullMQ id. Goldens use colons, which BullMQ forbids.

After: identity minted once, carried across

Enqueue seam (TS)

derives the only jobId → BullMQ job id

Py worker adapter

stamps job.id onto JobResult. Handler forgets the id rule.

Problem. ADR-0007 §2 idempotency depends on the jobId, but each world derives it independently: different separators, a copy-pasted hour-bucket rule and prefix map. Each side's tests assert its own format.

Solution. The backend enqueue is the only place a jobId is minted. The Python JobBus adapter passes BullMQ's job.id through, and the goldens switch to the legal form.

  • Delete the Python derivation outright
  • Locality: one id rule
  • Goldens stop encoding illegal ids
  • Persisted job_id joins BullMQ
04

Let the contract own each JobName's phase progression

Worth exploring in-process
  • packages/contracts/src/enums.ts: TechnicalPhase / FundamentalPhase
  • services/ai/src/tuju_ai/handler.py: phases tuple + literal "synthesizing-verdict" / "done", total = 5
  • services/ai/src/tuju_ai/contracts_generated/models.py: JobProgress.phase = union of both
  • apps/backend/src/jobbus/stub-job.worker.ts: stepTotal: 1

Before: phase knowledge sliced across 4 places

contracts enum: per-type set
generated model: union (tech phase OK on FA job)
handler: re-typed literals, total = 5
stub worker: total = 1
test_handler: hand-written order assert

After: one band

contract · per-JobName ordered phases

worker iterates it; stepTotal derives from it; conformance test checks emitted sequence

Problem. The contract declares the phases, the handler re-types them, and the generated union type lets a worker emit a fundamental phase on a technical job and still pass validation.

Solution. The contract publishes the ordered phase sequence for each JobName, and the worker and stub consume that sequence instead of re-spelling it.

  • Drift fails a test, not the UI
  • stepTotal stops being a magic number
  • Delete hand-written order asserts

Worth exploring, not Strong: the phase set is still a stub until the real LangGraph graph lands (ADR-0007 risk note).

Problem. If the key scheme in handler.py changes, every persisted symbol silently becomes 'unknown'.

Solution. The Postgres writer takes the symbol from what the backend already knows about the job and treats the pointer key as opaque.

  • Artifact stays opaque (ADR-0004)

Top recommendation

01 · Deepen the JobBus into the job lifecycle module

It fixes a live correctness bug (a request that dedupes onto an existing job never gets its result) and closes the largest gap between ADR-0007 and the code. It also gives #02, #03 and #06 their natural home, since correlation registration, identity and routing all converge on the same seam.
